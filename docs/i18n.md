# 다국어 (i18n)

`chattea-mobile`과 `chattea-web`은 `i18next` + `react-i18next`로 다국어를 지원한다. 기본 언어는 한국어(`ko`)이고 `en`, `ja`, `vi` 리소스를 함께 번들한다. 런타임에 리소스를 가져오지 않으므로 오프라인에서도 동작한다.

## 리소스 구조

```
apps/chattea-mobile/src/i18n/locales/{ko,en,ja,vi}/{common,auth,billing,chat,community,matches,notifications,profile,settings}.json
apps/chattea-web/src/i18n/locales/{ko,en,ja,vi}/{common,community}.json
```

- 로케일 × 네임스페이스 단위 JSON으로 Locize의 `{lng}/{ns}` 레이아웃과 동일하다.
- `ko`가 source of truth다. 각 `resources.ts`의 `match<Widen<typeof ko>>` 타입 체크 때문에 다른 로케일에 키가 빠지면 `tsc`가 실패한다.
- 앱 간 리소스는 공유하지 않는다. 네임스페이스·키가 겹치면 각 앱에 같은 키를 둔다(번들 크기와 독립 배포를 위해).

## chattea-mobile

- 엔트리(`index.ts`)가 `./src/i18n`을 임포트해 디바이스 로케일(`expo-localization`의 `getLocales()`)로 초기화한다. 지원하지 않는 언어는 `ko`로 폴백한다.
- 컴포넌트는 `useTranslation(ns)`을 `@/i18n`에서 가져와 사용한다 (`t("common:key")`로 다른 네임스페이스 참조 가능).
- 훅/유틸(Alert, 채널명 등)에서는 `i18n` 싱글턴을 임포트해 `i18n.t(key, { ns })`를 쓴다.
- 테스트에서는 `expo-localization`을 `test/mocks/expo-localization.ts` 스텁으로 대체해 항상 `ko`로 초기화된다.

## chattea-web (SSR)

- Fastify 라우트(`create-app.ts`)가 요청의 `Accept-Language` 헤더를 `resolveAcceptLanguage`로 해석하고, `<html lang>` 치환과 함께 `renderApp`에 `language`를 넘긴다.
- `entry-server.tsx`는 요청마다 `createI18n(language)`로 새 인스턴스를 만들어 `I18nextProvider`로 감싼다. 싱글턴을 공유하지 않으므로 동시 요청 사이에 언어가 섞이지 않는다.
- 서버가 정한 언어는 `window.__CHATTEA_LANG__` 스크립트로 tail에 주입되고, 클라이언트 엔트리(`entry.tsx`)가 그대로 사용해 hydration 불일치를 막는다. 값이 없으면(Module Federation remote, 직접 로드) `i18next-browser-languagedetector`가 `navigator`/`htmlTag` 순으로 감지한다.
- 프로바이더 없이 `useTranslation`을 쓰는 경로(MF `./CommunityApp`, `renderToStaticMarkup` 테스트)는 모듈 로드 시 생성되는 기본 인스턴스로 폴백한다 — 서버는 `ko`, 브라우저는 감지 언어.

## Locize 연동 준비

현재는 번들 리소스만 쓰고 Locize 호출이나 크리덴셜은 없다. 추후 `i18next-locize-backend`를 붙일 때는:

- 네임스페이스 JSON을 그대로 Locize 프로젝트에 업로드하면 된다 (`{lng}/{ns}.json` 구조 일치).
- 앱 코드에서는 각 `src/i18n` 초기화부에 backend 플러그인을 env(`EXPO_PUBLIC_LOCIZE_*` / `VITE_LOCIZE_*`)로 게이트해서 추가한다. env가 없으면 번들 리소스로 폴백하도록 유지한다.
- 프로젝트 ID/API 키 같은 비밀 값은 절대 저장소에 커밋하지 않는다.
